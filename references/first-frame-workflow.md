# 每段首帧与 HTML：可复用工作流

## 1. 三项选择与执行边界

用户提供视频后，进入以下流程。已经在本次任务中明确说过的答案沿用，不为了形式重复发问。关键选择没有回答时保持待确认，不以超时替代答案。

1. **拆解前确认主角**：“提示词中的主角要保留原样，还是替换为你指定的角色？”其他角色需要外观依据；若用户说有参考图，请上传。替换多个角色时建立原角色到新角色的映射，仅目标不明确时进一步询问。检查文件可读性、链接可达性可以先进行，内容拆解须等这项回答。
2. 完成视频分析和双语目标提示词。原片观察和目标改编分开，不能将生成补足写成原片事实。主角替换同时应用于双语视频提示词和首帧提示词；保留动作、镜头意图并适配结构。角色替换读取 [角色适配规则](character-adaptation.md)，查看用户提供的正式图及当前已确认设定。
3. **首帧生图前确认参考**：“首帧图片是否有希望使用的背景、场景或其他物品参考图？没有的话，我会沿用原视频的场景和物品。”请用户上传已有参考，并确认其控制的内容；已有明确用途时不用多问。背景替换导致环境和道具变化时同步调整目标视频提示词。
4. **首帧生图前确认批次**：“首帧图片一次生成全部，还是分批生成？分批可默认每批 3 张，也可指定数量。”可以与参考问题在同一次对话中提出。用户选分批但未给数量时，告知采用每批 3 张并执行首批，无需再问一次。

用户明确只要提示词时停在提示词交付；明确只做某几张时不扩展到整套。完整工作流会自动进入首帧和 HTML 阶段，但必须先收到参考与批次选择。不因使用某条 Skill 就自动批准收费 API、视频生成或发布操作。

## 2. 文件化状态与继续执行

在项目的 `output/video-workflows/<本次任务短名>/` 保存 `workflow.json`，承载实际数据而非空白模板。至少包括：

- 原视频来源、实际访问及分析范围、已知画幅、音轨核验状态。
- 主角选择与映射、角色/背景/道具参考的本地路径、各自控制范围。
- 参考选择和批次选择是 `pending` 还是已确认，模式 `all` / `batch`，每批数量，以及本次授权处理的镜头范围。
- 按真实分段数量记录稳定编号、原片近似时间、动作分析、目标中文/英文视频提示词、生图提示词、首帧原图路径、状态 `pending` / `generated` / `checked` / `failed`。
- 当前批次、下一批起点及最终 HTML 路径。
- 每段 `attachments`：顺序、提示词标识、真实文件路径、版本、用途及角色 ID；首帧验收或参考变更后同步更新双语提示词和清单。
- 各批次的用户验收状态 `pending` / `changes_requested` / `approved`、对应图片版本及用户明确确认内容。工具自检 `checked` 不等于用户验收；修改或重新生成后，该批验收状态恢复 `pending`。

续做时先读取此记录和已有素材。用户改背景、主角或道具时，只更新受影响的提示词和图片，保留旧版为兄弟版本，不用旧图冒充新版本。用户已确认的阶段选择无需再次收集。

**全量模式**：将所有计划首帧作为一批生成，期间报告进度，不在每三张后人为拆批。一次全部生成表示交付范围，不表示拼成一张多宫格；每段仍生成独立图像。完成后展示整批图片并等待用户明确确认无需修改，验收前不进入最终 HTML 整理。

**分批模式**：完成当前一批后展示图片，说明已生成/总数、已验收数量及下一批编号，保存状态并暂停。询问：“本批首帧是否无需修改？确认无需修改后，我会继续下一批（最后一批则整理 HTML）。”用户明确表示“无需修改，继续”“本批确认通过”等才记为 `approved`，随后执行下一批，无需再次询问批次和既有参考。仅回复“继续”或“好的”等未明确验收的内容时，简短确认本批是否无需修改，不自行推断通过。

用户要求修改时先记录 `changes_requested`，完成指定修改，展示新版本，恢复 `pending` 并再次等待用户验收；不能在改图后自行认定通过。最后一批同样要经过这一环节。用户确认最后一批无需修改、且全部批次验收完成后，才自动整理 HTML，无需另等“做 HTML”。

## 3. 参考分工与连续性

先实际查看每张参考图，不只读取文件名。给生图工具的提示词要写明参考作用：角色图控制身份和结构；背景图控制场景；物品图控制道具外观；已生成首帧辅助连续性。角色正式图优先于候选首帧，防止错误被逐张放大。

场景与物品参考不是一律复制整个背景。按用户要求提取指定属性，说明哪些沿用原视频、哪些来自新参考；新提示词不得残留被替换场景。可选参考图没有提供时，不强行要求上传。

镜头数量以实际视频为准，不固定为 12 段，画幅不固定为 9:16，乡村菜园、烹饪和橘猫不是此工作流的默认素材。默认沿用当前视频画幅，逐段保持角色外观、耳色方向、身体结构、环境、光向、道具及尺寸关系；只有原视频切镜或用户改编需要时才改变。

## 4. 从视频动作转为首帧

生图提示词描述该段动作的**可执行起始状态**，不是用整段动作或高潮结果代替静帧。例如，准备倒调味汁时瓶口刚开始倾斜，装碗时勺子停在碗上方，吃面时面条刚靠近嘴边。

- 给后续移动留出画面空间；工具、接触点、运动对象及必要肢体可见。
- 维持动作起点与该段视频提示词一致。已有首帧处于稍后的姿态时调整视频起始描述，或修正图片，不能要求从互相冲突的状态开场。
- 保持主体身体结构。短四肢角色通过机位、桌高、道具尺度与接触位置适配，不拉长身体。不得自动把原角色的尾巴、条纹、手指或服装迁移到新主角。
- 每段独立输出完整图像，不做拼贴、分镜联系表或带界面的截图，不自动添加文字水印。
- 使用当前可用的内置生图功能；遵循 imagegen 的参考查看、调用、保存和失败处理要求。生成失败时记录失败镜头，已有成品保留，不能用文字占位符冒充完成。

逐张检查身份、结构、参考控制、起始姿态、道具握持、构图和画幅。需要修正时针对具体问题迭代；同一问题连续两次修正仍失败则报告并保留当前结果，不无限重试。最后交付如有未解决问题需明确列出。

## 5. 原图保存与自动 HTML

每段最终选定的原始图像复制到本次任务的 `images/`，用稳定编号命名（如 `01-kneading.png`）。保留生成文件的原始像素、格式和字节，不通过截图、缩略图、重采样、裁切或二次压缩来制作交付原图。保留生成提示词和引用素材对应记录。

完整工作流中所有计划镜头均已生成、检查且每批（含最后一批）均已被用户明确确认无需修改后，自动创建 `index.html`。用户明确要求提前预览时可提供 HTML 草稿，但缺图、失败或仍有待验收批次时必须标记草稿，不能声称整套完成；草稿不替代逐批验收。已有指定 HTML 则在其对应位置更新，不另造无关网页。

生成最终 HTML 前，按 [附件绑定与上传顺序](attachment-binding.md) 将每段真实首帧及角色/环境/道具参考明确写入最终双语提示词，逐段展示附件上传清单与原图入口，并在交付时提醒用户按编号顺序上传。

HTML 内容：

1. 视频来源、实际分析范围、角色及参考选择、必要适配。
2. 分镜表：稳定编号、原片时间、动作和镜头说明。
3. 完整中文提示词合集；每段前插入对应首帧原图。
4. 完整英文提示词合集；同样按镜头编号插图，两种语言各自集中呈现。
5. 单段及整组复制按钮，查看完整原图/下载原图入口；必要的生成设置、衔接说明和限制。

显示尺寸可以通过 CSS 缩小，原图保持原始分辨率和完整画面，使用等比 `height:auto`，不以 `object-fit:cover` 裁切画面。图像标为“生成首帧”，不能称为原视频截帧。

默认生成本地 HTML 加 `images/` 文件夹，采用相对路径并将整套打包为 ZIP，方便用户移动和分享。若用户要求单个自包含 HTML，则把原始图片字节无损嵌入；不为控制 HTML 体积而压缩原图。无需部署到公网。原片提示词若保留，另标为原片分析；用户的目标提示词必须匹配首帧角色及新参考。

HTML 转义用户文字、链接和提示词；复制逻辑使用纯文本，JSON/JS 中的换行正确转义，不拼接未转义外部内容为脚本。普通图片查看与下载可用原图链接，浏览器限制复制时提供文字选中或手动复制方式。

## 6. 完成检查与交付

确认每批用户验收状态为 `approved` 且对应当前图片版本，再检查计划镜头数与成品数一致，双语镜头编号、图像对应和角色一致，图片路径全部存在，PNG/JPEG 等原图字节未被变换。检查 HTML 和脚本语法；有可用浏览器预览时核对图片加载、移动端排版及复制按钮。不能预览时如实说明验证范围，不声称已视觉测试。

全量完成后交付 HTML 与完整 ZIP 链接、图片总数及必要的未解决限制。分批中间阶段只交付当前批次和清楚的进度，最后一批获用户确认无需修改后自动完成以上整理。后续用户修改沿用相同工作目录和状态继续。
